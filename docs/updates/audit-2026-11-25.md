# Audit: stability, rendering and memory on the Radeon 780M (2026-11-25)

Branch `laptop/780m` on arnoudstorm/VIctory, last code commit `00b6f89`.
Laptop: Radeon 780M, 16 GB shared RAM (~5.9 GB D3D12 budget), screen
2880x1800 at 120 Hz, Windows 11. Diagnostics build, Series S profile,
settings of `run-laptop.ps1`. Every game run was automated (no one watched
the screen). Numbers are measured unless marked as calculated.

## 1. Start-screen strobe (`7d0ed69`, `docs/updates/flicker-audit.md`)

- Cause: the title decodes the start-screen video into a ring of three
  textures through a second view of their pages. VIctory watches a
  texture's pages through a guard that does not see writes through
  another view, so it took the slot as unchanged and re-hashed it only
  every 8th frame.
- Fix: VIctory counts the views of each page; textures on aliased pages
  are hashed on every check. Unit test `inplace::alias_tests`. Cost: 3-6 ms
  of texture refresh per frame on the start screen. No GPU wait added.
- Measured, frames 300-967: jumps of 20+ (of 255) 67 -> 22, opposing pairs
  60 -> 12, most in 30 frames 24 -> 6. Timed against the clock: 1 flash in
  194 s while capturing at 3.4 fps.
- Left: black frames at the start of loading (not tied to low memory: one
  came with 1.5 GB free and one draw). **Not a photosensitivity
  certification**: only brightness changes were counted.

## 2. Startup and menu stability (`docs/updates/stability-780m.md`)

- 3 of 3 startups: start screen in 4-39 s, no errors, window switching
  works, frames keep coming at ~30 fps with the game in the background.
- With no input the title starts its world load after 55-80 s; the
  first run (150 s) ended out of memory at 116 s.
- "Not responding" always starts when free RAM falls below ~1 GB and
  Windows trims the game's working set; shader translation is not the
  cause (all shaders came from the disk cache).

## 3. Resolution, HDR and presentation (`docs/updates/resolution-hdr-780m.md`)

- `VICTORY_DISPLAY_MODE` at 3840x2160, 1920x1080 and 1280x720: the same
  planes (1920x1080 game, 3840x2160 UI), the same 4K swap chain, the same
  memory peaks. The title picks its sizes itself.
- HDR is answered "SDR"; one 60 Hz mode; no frame limiter. None of these
  can be measured as a variable now.
- Swap chain at window size would save ~25 MB (calculated); not done.
- 540p at 20 fps is not realistic: the internal resolution can not be
  lowered from VIctory, and the world load is memory bound.

## 4. World-load memory (Phase 5)

Where the card's memory is at the world-load peak (VIctory's own counts,
6 runs):

| Part | Size |
|---|---|
| Host copies of title memory | 2.4-3.7 GB, of them windows outside buffers 1.8-3.1 GB |
| Render targets and what the host writes | 1.0-1.2 GB |
| Textures the title fills | 0.3-1.2 GB (depends on how much streamed in before the world) |
| Command lists (process memory) | ~0.9 GB without lazy lists |

Findings:

- **Why the windows are copies:** 6,960 windows were turned down for
  in-place use because the title's memory is section views, which
  Direct3D can not open in place (`OpenExistingHeapFromFileMapping`
  refuses the reserved page pool). Of the windows' 2.5 GB, only 1.4 GB of
  pages were ever copied; 341 asks without a length hold 920 MB (each
  runs to the end of its 4 MiB cell).
- **Command lists:** an empty host list costs 1,337 KiB, of which ~1.1 MB
  is the driver's first block of command memory when the list is opened
  (an allocator alone: 11 KiB). 620 of the title's 633 lists are not used
  before its world.
- **Upload buffers 504 -> 4,956:** they rise with the textures the title
  fills, when it starts streaming its world before the load. When this
  happens varies from run to run (40-110 s). It looks like streaming, not
  a leak, but it was not traced buffer by buffer.
- **RAM, card, commit and paging, kept apart:** commit is not the limit
  (41-42 GB of 45 GB). Free RAM falls to 20-500 MB, the game's working
  set is trimmed (3-5 GB of 12 GB private in memory), and Windows reads
  0.4-0.8 GB/s from the page file. The card is 0.5-1.8 GB over its budget.
  Device removal or out-of-memory follows; which one depends on which
  allocation fails first.

Experiments, one variable each (130-150 s, no keys):

| Experiment | Result | Kept |
|---|---|---|
| `VICTORY_LAZY_LISTS=1` | Start screen: the card 2,051 -> 1,524 MB, private 6,785 -> 6,046 MB, free RAM 2.1 -> 2.9 GB. World peak unchanged (7.3-7.6 GB) | **Yes**, opt-in, on in `run-laptop.ps1` |
| `VICTORY_PRELUDE_POOL=1` | Preludes alive in the world 447-458 -> 22-25; no change in the totals above the noise | Opt-in, off |
| Both | Most free RAM at the start screen (4.4 GB); world peak 6.8-7.7 GB; the freed room filled with ~1.2 GB more streamed textures | - |
| Both + texture share 75 -> 50% | No change (textures ~0.7 GB, peak 6.4-7.7 GB) | **No**, reverted (setting only) |

Found on the way: **submitting a `CreateCommandList1` list that was never
opened removes the device on the 780M.** The regression test
`lazy_list_tests` caught it before any game run; VIctory never submits
such a list.

Not met: **the card below 5.9 GB, 1 GB of free RAM held, no device
removal / out-of-memory.** Every run still ends over budget at the world
load.

## What would move the world peak (in order)

1. **Windows that hold only the pages read:** 1.0-1.1 GB of window bytes
   are never copied. Reserved (tiled) buffers backed only where copied
   would save that much; this is an architectural change (copies into
   unbacked tiles are dropped, so every copy path must map first) and was
   not started.
2. **The page pool as a committed section:** it would let the title's
   memory be opened in place (no copies at all for view memory). An
   earlier try (`VICTORY_POOL_COMMIT=1`) placed only ~150 MB more,
   because windows spanning views can not be one buffer; needs a design.
3. **Asks without a length** (920 MB): a bound from the shader's actual
   reach instead of the 4 MiB cell's end.

Status: item 1 is designed and its probes pass
(`design-tiled-windows.md`, `08e9f1b`), left to the other developers.

## 5. Lifetimes and duplicate allocations (follow-up)

Run `p5-owners` (140 s, no keys, lazy lists on). Diagnostics builds now
log where each block of 32 MB or more of VIctory's own heap is made.

| What | Size | Whose |
|---|---|---|
| Biggest block | 251 MB | the title's audio memory (`audio::ApuAlloc`), asked for by the title |
| Next | 82 MB | title memory of a committed resource (`xmem::XMemAllocDefault`) |
| 3 blocks | 114 MB each | loading the executable (`victory_loader`), at the start |
| 19 blocks | 34-68 MB each | hash tables of the shader translator (`victory_shader::structure::Bools`), while shaders translate; let go after |
| 934,000 blocks under 4 KiB | 144 MB | bookkeeping |

- **Windows are reclaimed, not leaked:** 2,789 windows (2,585 MB) were let
  go in 140 s. Of the 2,377 MB alive, 2,273 MB are held by the title's
  live command lists or the pass over the heap: they stay because the
  title's lists still name them.
- **Render targets** (1.0-1.2 GB) are VIctory's own committed textures
  beside the title's placed resources in its page pool. Whether the
  title's pages under them are resident (RAM) or only committed can not be
  told from VIctory's counters; not resolved.
- **Black frames** (`a black frame after a frame that was not`): 4-7 per
  run, at the start screen with 1.5 GB free as well as at the world load.
  Not tied to low memory; whether the title draws them is still open.
- No duplicate allocation found that VIctory could drop without one of
  the designs above.
