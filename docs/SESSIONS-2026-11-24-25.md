# VIctory on a Radeon 780M laptop: the sessions of 24-25 November 2026

One document for everything done on this fork in these sessions: what was
set up, what was measured, what was changed, and where it stands. Every
number comes from a run's own log or a test on the machine below; what
was not run is said to be unverified.

## The machine

| | |
|---|---|
| CPU / GPU | AMD Ryzen 7 8840HS with Radeon 780M (RDNA3, integrated) |
| Memory | 16 GB, shared with the GPU (512 MB carved out; Direct3D budget ~6 GB) |
| OS | Windows 11 Home; Smart App Control off (it blocked every Cargo build); `TdrDelay` 60 s (was 2 s) |
| Title | Series X\|S build 1.0.2.1 (BLAKE3 `b99f876b74d4a77f…`), run in Series S mode |

**What ends every run:** the PC's 16 GB. When the world's first scenes
stream in, the process holds 12-13 GB, the PC has 0-400 MB free and the
card's share is 1.0-1.6 GB past its budget. Depending on which allocation
fails first it shows as out-of-memory or as a device reset (updates 1-4).

## Settings measured

| Setting | Result |
|---|---|
| Series S instead of Series X | Series X ran out of GPU memory in the menus (4K targets) |
| Shader loop limit 64 | shorter GPU submissions (needed before `TdrDelay` was raised) |
| Wide refresh / copy-back, joined copies | world frames 6.8 s → 2.3 s; CPU copying 6.4 s → 0.3 s a frame |
| Relay (`VICTORY_RELAY=2`) | 2.3 s → 1.2 s a world frame; not what ends runs (test 4) |
| Window grid 4 MiB → 256 KiB → 64 KiB | 2.8 → 2.4 → 2.2 GB, but 64 KiB costs ~0.4 ms of CPU and ~33 KiB per buffer: 256 KiB |
| 96 lists in the air (default 256) | no measurable change |
| `VICTORY_TEXTURE_ROOM_PERCENT=75` | no effect: a 2 GB floor came first (fixed by `14bbc4b`) |
| Closing Discord, ChatGPT, Chrome, Spotify, Steam, OneDrive | ~9-10 GB of commit back before each run |

## Synthetic measurements (no game data)

| Test | Result on the 780M |
|---|---|
| shared buffers made and freed | the card gets everything back; nothing left parked for its submission |
| leak or driver reuse | 256 MB kept by the driver, the same every round: not a leak |
| a submission and its wait | 1.1 ms |
| copies between shared buffers | 24 GB/s |
| cost of a small shared buffer | 0 on the card; ~33 KiB of process memory and ~0.4 ms each at 64 KiB |
| what a host command list keeps | ~1.3 MB after 20,000 commands, over a reset |
| a run of a section in place | the card reads the title's bytes and the title sees the card's writes, no copy |

## Where the memory goes in the world

| Part | Size |
|---|---|
| copies of title memory | ~3.0-3.1 GB (windows ~2.4-2.5 GB) |

window lies inside one view; 939 MB of windows lie in one run of a section

## Where it stands

- Reached: menus, past the start screen, the world within 1-2 minutes, up
  to ~3,800 draws a frame at 0.4-2 fps, with the cutscene's start seen on
  screen.
- Not reached: staying in the world. Every configuration measured runs
  the 16 GB PC out of memory within a minute or two of the world.
- Not settings: each lever left has been measured above and moves the end
  by at most a few hundred MB.
- What would: sending every request over a run of the page pool to one
  placed buffer (the second view of `d745458` is in place and tested;
  what is missing is the routing, so that copies are no longer made beside
  it), or 32 GB of RAM.
